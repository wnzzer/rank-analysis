# 标注反驳：AI 回应玩家的理由 设计

日期：2026-11-21
状态：已口头批准（入口、表达方式、不改判、一轮、结构化输出）

## 目标

玩家标注「最关键 / 最犯罪」后，和模型有分歧时现在只是并排摆出两个结论，到此为止。
这次补上后半段：玩家写理由，AI 针对理由回应一次。

三个目的，按优先级：

1. **情绪价值**。玩家觉得被听进去了，而不是被数据怼回来。
2. **收集模型漏算的点**。玩家反驳得最多的地方就是评分该补的地方（如全程单带不参团）。
3. 为后续的「你 vs AI」争议分享卡提供内容（另开设计，不在本次范围）。

### 不做的事

- **不改判**。标签和分数始终来自评分计算；AI 认账也不改结论。吵赢了就改分会毁掉评分的公信力。
- 不做多轮对话，不做聊天界面。
- 不做快捷理由选项。
- 不做争议分享卡。
- 弹卡上不放入口（340×184 放不下输入与回复）。

## 流程

入口只在标注卡 `components/record/review/LabelCard.vue`。对局页战报与复盘页共用该组件，两处都有。

提交标注后分三种情况：

| 情况 | 表现 |
|---|---|
| 与模型完全一致 | 与现状相同，不出现反驳相关元素 |
| 有分歧，且说明不少于 4 个字 | 自动触发。对比行下方显示「AI 正在看你的理由…」，随后换成回复 |
| 有分歧，没写说明或不足 4 个字 | 对比结果下方出现「不服？说说理由 ›」，点击回到编辑态并聚焦说明框；重新提交后触发 |
| 有分歧、理由够长，但还没有回应（如上次调用失败后重新打开） | 同一位置显示「让 AI 回应你的理由 ›」，点击直接触发 |

「有分歧」= 玩家选了的项里至少一项与 `modelPicks` 不同。两项都有分歧时一次回应里一起讲。

说明框提示文案由「可选：说说理由，比如…」改为「说说理由，AI 会回应你，比如…」。

**一局只保留一条回应。** 点「修改」改了选择或说明并重新提交时，若仍有分歧则重新调用，旧回应被替换；
选择与说明都没变则不重新调用。

### 回复区

- 立场标签：`concede`「你说得对」（绿）/ `partial`「有一部分道理」（黄）/ `hold`「我还是这么看」（中性）。
- 回复正文，约 100 字，上限 200 字。
- 「反馈去向」一栏，**按真实的上传状态显示**（界面拼接，不由模型生成）：
  - 已上传：「✓ 已反馈成功」+ 一句具体的话——玩家点了「还是不服」时说「你不服的这条已上传。这类反馈对改进评分最有用。」；
    AI 认账时说「评分漏算的这一点已上传，会用来改进评分。」；其余说「你的看法已上传，会用来改进评分。」
  - 只在本机（没同意分享）：「这条反馈还只存在你的电脑上。」+ 按钮「上传反馈，帮忙改进评分」。
    点击等同于同意分享对局判断（写入 `matchLabelShare`），并立即上传这一局；按钮旁说明传什么、可在设置里关闭
  - 上传失败：「上传没成功，这条反馈目前只在你的电脑上。」+「重试上传」

  初版在认账时固定显示「这条已记下，会用来改进评分」，而没开分享的玩家那条反馈并没有离开他的电脑。
- 两个按钮：「说得有道理」「还是不服」。点击后记录玩家态度并变为已选状态；不触发任何调用。可改选。

## AI 调用

### 方式

一次调用、结构化输出、不流式。复用现有通路（`stream_ai_analysis` 的 DashScope `response_format: json_object`；
Claude 通路按提示词约束输出 JSON）。模型沿用用户在设置里选的 AI 提供方，新增场景 `labelRebuttal`，
默认模型与复盘点评 `STAGE2_MODEL` 相同。超时 20 秒。

返回结构：

```ts
interface RebuttalReply {
  stance: 'concede' | 'partial' | 'hold'
  category: RebuttalCategory
  reply: string
}

type RebuttalCategory =
  | 'absence' // 团战缺席 / 单带
  | 'targeted' // 被针对
  | 'empty_stats' // 数据好看但没作用
  | 'attitude' // 挂机、送、摆烂
  | 'draft' // 英雄或阵容问题
  | 'teamwork' // 沟通配合
  | 'other'
```

### 给模型的材料

1. **分歧项**：每个分歧项里玩家选了谁、模型选了谁。
2. **涉及玩家的事实卡**（2～4 人）：位置、英雄、胜负、KDA、七个分项的档位词（`plainScore.levelOf`）、
   阵亡归责明细（有时间线时）、`shareFacts` 为该玩家生成的事实。不给原始分数。
3. **评分说明**（固定文本，随代码维护）：每个分项看什么，以及明确不看什么。初版「不看」清单：
   - 团战缺席只影响本人团战分项，不追究缺席导致的队友阵亡
   - 推塔伤害计入资源分项，不与同期队伍损失对冲
   - 不看英雄克制与阵容搭配
   - 不看语音、打字、信号等沟通与态度
   - 不看装备选择与出装顺序
   - 时间线缺失时没有阵亡归责
4. **玩家的理由原文**。

评分逻辑变化时必须同步更新「评分说明」，否则模型会对已经算进去的东西认账。

### 对模型的要求

立场是**站在玩家这边的队友**，不是解释评分的裁判（初版按裁判写，真机反馈「情绪价值不高」「没拍对马屁」）。

- 开口先替玩家说话，并拿事实卡里对他有利的数据撑腰（如参团率、资源在场率）。
- 理由指向「评分说明」里写明不看的东西 → 明说是评分的盲区。
- 不提玩家本人的任何失误。**玩家本人的事实卡只放对他有利的事实**（领先的分项、情有可原的阵亡）：
  只靠提示词禁止不够，模型手里有负面数据就会说出来。
- 不夸、不替玩家指的那个人开脱；可以就事论事说那个人哪里没做好，不做人身攻击。
- 事实与玩家说法对不上 → 不纠正、不说教，挑能支持他的部分说；但不附和数据明确否定的说法，不编数据。
- 不承诺改判，不给「应该判给谁」的结论。

`stance` 只用于后台统计（数据是否印证玩家的说法），与语气无关。

### 校验与保底

复用 `matchDetail/postprocess.ts` 的 `extractNumbers`：回复正文里出现的数字必须都能在事实卡文本里找到。

以下任一情况整条作废，改用保底：JSON 解析失败、`stance` / `category` 不在枚举内、`reply` 为空或超过 200 字、数字校验不过。

保底：立场记 `unknown`，类别记 `other`，正文为「你的理由已记下。这局的判断依据可以在完整复盘里看到。」，
不显示立场标签，仍显示两个态度按钮。

## 数据

### 本地

`MatchLabel`（Rust `command/match_label.rs` 与前端 `services/matchLabel.ts`）新增可选字段 `rebuttal`：

```ts
interface MatchLabelRebuttal {
  stance: 'concede' | 'partial' | 'hold' | 'unknown'
  category: RebuttalCategory
  reply: string
  /** 玩家对这次回应的态度；没点为 null */
  verdict: 'convinced' | 'unconvinced' | null
  model: string
  /** 回应针对的选择与说明的指纹：变了才重新调用 */
  basis: string
}
```

再次打开同一局时直接显示已存的回应，不调用。旧版本存下的标注没有该字段，按无回应处理。
回应相关的保存（回应到达、玩家点态度按钮）失败时不提示：标注本身早已存好，回应留到下次保存一并写入。

### 上传

沿用「分享对局判断」开关（`matchLabelShare`）。同意分享时多传四个字段，**回复正文不上传**：

`match_labels` 新增可空列：

| 列 | 类型 | 约束 |
|---|---|---|
| `rebuttal_stance` | text | in (`concede`,`partial`,`hold`,`unknown`) |
| `rebuttal_category` | text | 上述七个类别 |
| `rebuttal_verdict` | text | in (`convinced`,`unconvinced`) |
| `rebuttal_model` | text | 长度 ≤ 64 |

玩家点态度按钮后需要再上传一次（upsert 同一行）。老客户端不写这些列，不受影响。
建表语句追加到 `supabase/match_labels.sql`，保持可重复执行。

**上线顺序**：必须先在生产库加列，再发带本功能的版本。客户端上传时四个 `rebuttal_*` 键总是带着
（无回应时为 null，用来覆盖改判前的旧值）；列不存在的话整行会被拒，连标注本身都传不上去。
立场或类别不在白名单内时，客户端把四项全置为 null 再上传，同样是为了不让 check 约束把整行拒掉。

## 出错与边界

| 情况 | 处理 |
|---|---|
| 调用失败或超时 | 显示「AI 暂时没回应」+「重试」。标注已保存，不受影响；不写入 `rebuttal` |
| 结构或数字校验不过 | 保底（见上） |
| 没有可用的 AI | 与调用失败同样处理。前端无法预知 AI 是否可用（线上密钥是编译期注入的），所以入口始终显示，不可用时走「AI 暂时没回应」+「重试」 |
| 说明不足 4 个字 | 不触发；「不服？说说理由」入口照常显示 |
| 提交时与模型一致 | 不触发，即使写了说明 |
| 回应进行中玩家点「修改」 | 丢弃在途结果 |

## 模块划分

| 模块 | 职责 |
|---|---|
| `services/ai/review/rebuttal.ts` | 分歧判定、事实卡拼装、提示词、返回解析、校验与保底（全部纯函数）+ 一个调用入口 |
| `services/ai/review/scoringNotes.ts` | 「评分说明」固定文本 |
| `components/record/review/RebuttalReply.vue` | 回复区：加载 / 回复 / 失败三态与两个态度按钮（纯展示 + 事件） |
| `LabelCard.vue` | 触发时机、入口、把结果写回标注 |
| `services/matchLabel.ts` / `command/match_label.rs` | `rebuttal` 字段的存取与上传 |

## 测试

- `rebuttal.ts`：分歧判定、事实卡内容、JSON 解析、枚举与长度校验、数字校验、保底、`basis` 指纹。
- `RebuttalReply.vue`：三态渲染、立场标签、认账追加语、态度按钮的选中与改选。
- `LabelCard.vue`：三种提交情况、重新提交是否重调、无可用 AI 时不出现入口、回应进行中点修改。AI 调用用假数据替代。
- Rust：`rebuttal` 字段的序列化兼容（旧文件无该字段）、上传载荷不含回复正文。
- 真机：打几局，分别写单带、被针对、纯情绪三类理由，看立场与类别是否对路。
